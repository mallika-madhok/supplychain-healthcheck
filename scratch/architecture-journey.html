Canadian Apparel Import Pressure Monitor — v1 architecture

From public data to a live score, and every stop in between

This is the same journey a row of data takes through your pipeline, laid out as a first pass through data engineering: what runs, where, on what schedule, and the concept each stage is teaching you.

A number leaves a government server

extract · runs weekly

Your pipeline asks four public agencies for whatever's new: the NY Fed's supply chain index, the Bank of Canada's daily USD/CAD rate, and two Statistics Canada tables (import mix by country, clothing CPI). Nothing is uploaded by hand — a scheduled job in GitHub Actions does this every week, whether or not anyone visits the site.

tools

httpxstats_canGitHub Actions cron

concept you're learning

Extraction is the part of a pipeline most tutorials skip: real APIs are inconsistent, undocumented in places, and change on their own schedule. You're building the part that has to cope with that.

Raw pulls get saved exactly as received

land · runs weekly

Before anything is cleaned up, each pull is written to disk with a timestamp and its source's own release date attached. Statistics Canada revises recent trade data after the fact, so nothing here assumes this week's numbers are final — a later pull can add a corrected value without erasing what was known at the time.

tools

DuckDBraw / staging tables

concept you're learning

"Never overwrite raw data" is one of the load-bearing rules of data engineering — it's what makes a pipeline auditable and debuggable months later.

SQL models turn raw pulls into trustworthy tables

transform · runs weekly

dbt models reshape the raw data in layers: staging models rename and type columns and pick the latest known value per period, mart models compute the actual scoring inputs — the currency z-score, the origin concentration (HHI), the freight pressure index. Each model is a plain, readable SQL file.

tools

dbt-duckdbstaging → marts

concept you're learning

Layered SQL modeling — the industry-standard way analytics teams keep transformations readable, testable, and reusable instead of one giant unreadable query.

The pipeline checks its own work

test · runs weekly, before anything ships

dbt test and pytest run automatically. If a source went quiet, a country code is unexpectedly null, or the HHI math breaks, the run fails loudly here — before a bad number ever reaches a chart. This is the difference between a pipeline and a script that happens to work today.

tools

dbt testpytestsource freshness checks

concept you're learning

Data quality testing: the practice that turns "it worked when I ran it" into "it's safe to run unattended, forever."

The finished tables leave the pipeline as files

export & publish · runs weekly

The tested marts are written out as Parquet files into data/ and committed straight into the repository. That commit is the handoff point: everything before this line only you and GitHub Actions ever see; everything after this line is what a visitor's browser can reach.

tools

Parquetgit commitGitHub Pages

concept you're learning

Treating your data warehouse's output as versioned files, not a database you have to keep running — the trick that makes "free hosting forever" possible here.

A visitor's own browser becomes the query engine

serve & query · runs on every visit, on their device

Nothing runs on a server when someone opens the site. Their browser loads DuckDB‑Wasm, fetches the Parquet files directly, and runs real SQL locally — the headline score, the driver detail charts, and the what-if slider are all live queries against data that lives on their own machine for the length of that visit.

tools

DuckDB-WasmPlotly.jsplain JS, no build step

concept you're learning

The client can be the compute layer. This is what makes the "what-if" slider instant and free to run, no matter how many people use it.

Every number shown is auditable, always

transparency · visible on every chart, not a toggle

Next to every chart and table sits the exact SQL query that produced it, shown permanently — not hidden behind a "show query" button. Anyone, including a hiring manager three clicks in, can check that the number on screen is really what the query says it is.

rendered SQL panelraw result table

concept you're learning

Reproducibility isn't a README claim — it's a UI decision. Showing the query is what makes the transparency claim checkable, not just stated.

Why this shape matters for you specifically: every arrow on this diagram is a boundary a real data team also has — between "raw" and "trusted," between "scheduled batch" and "live query," between "computed" and "shown with proof." Building each boundary yourself, even at small scale, is what lets you describe this project as engineering rather than a demo.
